# 答辩前段文字稿：User Story 与结果展示

> 这是根据当前答辩构想重新打磨的前段演讲稿，不是 PPT 页面排版稿。  
> 建议演讲顺序：先讲用户为什么需要这种产品，再用动态 Showcase 证明它确实按这个设计工作。

## 一、User Story：从一次性答案到可演进的证据链调查

### PPT 页面标题候选

优先推荐：

> 用户想要的不是一个答案，而是一条可以被检查、修改和重新推导的证据链

其他可选标题：

- 当 AI 给出结论时，用户还能不能改动它的依据？
- 运维诊断不应只返回结果，还应保留探索过程
- 从“AI 猜根因”到“人机共同演进调查树”

### 屏幕文字建议

页面只保留这一组短句：

```text
用户目标：自主完成定位分析

市场问题：
无效证据仍被使用
错误假设持续推进
探索路径被隐藏

Mini-Drop：
假设驱动 · 证据为核 · 动态演进
```

画面上建议放一棵调查树，而不是放系统组件图：

```text
Incident
   ├─ H1：CPU 饱和
   │    ├─ E1 支持
   │    └─ E2 反证
   └─ H2：下游连接等待
        ├─ E3 支持
        └─ E4 待验证
```

### 演讲稿（推荐版本）

用户使用运维产品，期待的不只是看到一段 AI 生成的分析，而是能够在 AI 协助下，持续完成一次真实的定位调查：提出问题，形成假设，获取证据，比较不同解释，最后得到一个有依据的结论。

但我们观察到，主流运维 AI 产品在处理这类问题时，往往存在三个缺陷。

第一，**无效证据可能继续留在推理上下文中**。例如时间窗不匹配、目标实例不一致、采集不完整的日志，仍然会被后续回答当成支持信号。

第二，**已经明显被反驳的假设仍可能继续推进**。系统没有把“假设被证据否定”转化为调查状态，模型就可能沿着错误方向继续采集和解释。

第三，**系统只展示最终结论，却隐藏了中间探索路径**。用户看到了一个根因，却不知道系统比较过哪些假设、舍弃过哪些证据，也无法判断结论是否依赖某个已经不可信的中间节点。

因此，Mini-Drop 不是把监控数据一次性提交给模型，而是尝试构建一个以假设为出发点、以 Evidence 为核心结构、可以持续演进的 AI 调查服务。

这里还有一条重要的证据可见性原则：**AI 能使用的 Evidence，不是系统默认全量注入的，而只能来自两种路径：AI 根据当前 Evidence Gap 自行申请并获得的证据，或者用户明确添加到当前调查中的证据。**

这意味着“系统里存在某条 Evidence”和“当前 AI 可以使用某条 Evidence”是两件不同的事情。Evidence 必须先经过当前 Case、目标范围、时间窗、Review 状态和分支可见性检查，才能进入本轮上下文。

在这个服务中，AI 可以提出假设和证据缺口，用户也可以随时介入：修改假设、排除错误 Evidence、否定某条因果边、调整目标范围，或者要求系统重新验证一条调查路径。

当中间某条证据或推理关系被判定为无效时，系统不会简单覆盖最终答案，也不会物理删除全部历史。它会让依赖该节点的中间 Claim、Hypothesis 或 Conclusion 失效，保留前后仍然独立有效的证据，从最近的有效祖先重新开启调查，形成新的推理代次。

这意味着，用户改变的不是一个 UI 上的置信度数字，而是整个调查树中某个节点的有效性。系统会根据依赖关系传播影响，保留历史，隔离失效路径，并重新组织后续的因果假设。

此外，我们还设计了**证据隔离**。不同探索分支默认只能看到公共初始 Evidence 和自己产生的证据，不能直接读取其他分支的假设、工具结果和中间结论。只有经过显式授权、范围和版本校验后，证据才可以被共享。

因此，不同调查链路之间不是“默认共享、再通过 Prompt 提醒模型谨慎使用”，而是**默认独立、显式共享**。一个分支产生的 Evidence 不会自动出现在另一个分支的上下文中；只有用户或治理流程明确执行共享，且目标身份、时间窗、Collector 版本、Review 状态和 Projection hash 均通过校验后，证据才进入另一个分支。

这样做的目的，是避免一个分支的早期猜测污染另一个分支，也让不同调查策略能够在相同初始条件下被公平比较。

### 这一页的收束句

> Mini-Drop 的核心不是让 AI 更快给出一个根因，而是让每个根因判断都能回答：它基于哪些证据、经过哪些假设、哪些部分仍然有效，以及如果中间事实被推翻，系统能不能重新推导。

## 二、复杂 User Story 的具体演示设定

为了让上面的设计不是抽象概念，建议使用一个复合事故贯穿后续 Showcase：

> 生产环境的 checkout 服务从上午开始出现间歇性超时：首页仍然正常，但购物车和支付链路受到影响；部分实例 CPU 偏高，同机邻居也出现波动；日志同时出现连接等待和请求堆积。值班 SRE 希望 AI 自动调查，但不允许修改生产环境。

这个场景同时包含：

- 现象不完整：服务没有完全宕机；
- 信号冲突：CPU 高不一定是根因；
- 多个候选假设：CPU、Runtime、IO、下游依赖；
- 证据质量问题：实例、时间窗和采集完整性可能不一致；
- 安全约束：只读调查，不允许恢复动作。

因此它可以自然引出：假设树、Evidence Gap、主动补证、分支隔离、人工排除、局部失效和重新调查。

## 三、结果展示：用动态状态变化证明设计有效

### PPT 页面标题候选

优先推荐：

> 我们展示的不是一段回答，而是一棵调查树如何被证据推动、被人工修正并重新演进

其他可选标题：

- 从 Evidence 进入到结论重验证：完整调查过程展示
- 结论会变化，但历史不会消失
- 当一条证据被排除，系统如何重新调查？

### 页面主叙事

结果页以 Web 前端动图/录屏为主，PPT 只显示一条状态链：

```text
用户问题
  → 初始假设树
  → Evidence 进入
  → AI 形成阶段性结论
  → 用户排除错误 Evidence
  → 依赖节点失效
  → 保留独立证据
  → 新一代调查重新展开
```

Evidence 进入当前调查只有两个入口：

```text
AI 申请并获准的 Evidence
              或
用户明确添加的 Evidence
```

其他链路的 Evidence 默认不可见，不能因为“系统里已经存在”就自动注入。

### 动态展示脚本

#### 状态 1：创建调查

画面展示：Case、服务、环境、时间窗、只读策略。

演讲：

> 用户只需要描述问题并给出调查边界。AI 不直接获得主机权限，而是在这个 Case 范围内开始构造假设和证据目标。

#### 状态 2：形成多条假设

画面展示：CPU、Runtime、下游依赖三个候选节点；每个节点有支持证据和缺口。

演讲：

> 系统不把第一个异常信号直接当成根因，而是保留多个候选解释，并明确下一步需要区分的事实。

#### 状态 3：Evidence 进入调查树

画面展示：Evidence ID、来源、目标、时间窗、Projection、引用字段。

演讲：

> 采集结果不是一段聊天文本，而是进入 Case 的 Evidence。但只有 AI 自行申请并通过门禁的证据，或者用户明确添加的证据，才会进入当前调查上下文。每条证据有来源、目标、时间窗、hash 和投影，结论必须引用具体字段。

#### 状态 4：形成阶段性结论

画面展示：`PARTIALLY_CONFIRMED`、支持边、未解决 Gap。

演讲：

> 当前证据支持某个方向，但仍有未排除的替代假设，所以系统给出部分确认，而不是把单条信号包装成绝对根因。

#### 状态 5：用户排除错误证据

画面展示：Evidence 从 `ACTIVE` 变为 `EXCLUDED` 或 `LOW_TRUST`。

演讲：

> 用户发现这条证据时间窗不匹配，或者目标身份不正确，因此将它排除。这里不是删除一个页面卡片，而是改变了证据的推理准入状态。

#### 状态 6：局部失效与重新演进

画面展示：关联 Claim/Conclusion 变为 `STALE_INPUT`，Workspace 变为 `RECHECK_REQUIRED`；不相关的 Evidence 仍保留。

演讲：

> 系统只让依赖错误证据的推理节点失效，前后独立有效的 Evidence 继续保留。随后从最近的有效祖先创建新的调查代次，重新检查替代假设。

#### 状态 7：分支隔离对比

画面展示：Branch A 和 Branch B；A 被排除的 Evidence 不影响 B，公共证据仍可见。

演讲：

> 这一步展示证据隔离的价值：一个分支被纠正，不会把另一个独立探索路径一起污染。不同链路默认独立，只有用户或治理流程显式共享并通过身份、时间窗、版本和信任校验后，证据才进入其他分支。

### 结果展示收束句

> 这条动图证明的不是“模型回答得像不像人”，而是系统能不能在证据变化之后，准确知道哪些推理仍然有效、哪些推理必须重做。

## 四、赛道对比与成功率展示

### PPT 页面建议

动态展示结束后，再切换到一张非常简洁的对比页：

```text
不同赛道 / 不同 Agent
        ↓
统一场景、统一指标、统一预算
        ↓
结果对比 + Mini-Drop 特色
```

不要只放一个“总分”。建议拆成四类指标：

| 维度 | 要回答的问题 |
|---|---|
| 定位能力 | 是否找到正确的实体、机制和影响范围？ |
| 证据能力 | 是否引用了正确 Evidence？是否覆盖关键事实？ |
| 调查能力 | 是否选择了有价值的下一步？是否避免无效采集？ |
| 可信与安全 | 是否正确处理反证、缺证、越权和拒答？ |

### 结果页演讲稿

在结果比较中，我们不只比较最后的根因文本，而是把能力拆成定位、证据、调查效率以及可信安全四个维度。这样可以区分：一个产品是猜中了结果，还是实际获取了支持结果的关键证据；也可以区分它是否会在证据不足时正确停止。

不同赛道的结果需要使用统一的场景、统一的预算、统一的停止条件和统一的评分口径。PPT 上展示你最终确认过的赛道分数，并在图例中写清楚数据集、运行次数和评测性质。

当前已有结果可以作为旁证，但必须标注边界：

- Evidence-native 9×3 结构链路：`27/27` 轮完成并通过结构门禁；
- 第二轮完整 Evidence ID/hash 引用：`27/27`；
- 公开 PR、非双盲人工质量粗评：约 `9.2–9.6/10`；
- 这些数字不能直接写成通用 RCA 准确率。

### 个人亮点的推荐表达

不要只说“我实现了很多功能”，建议归纳成三个个人贡献：

```text
1. 把证据从 Prompt 附件设计成可治理的产品对象；
2. 让 AI 只能使用“自行申请或用户添加”的 Evidence，默认不拥有全局证据；
3. 把用户纠正转化为调查树的局部失效和重新演进；
4. 把独立链路、显式共享、引用验证和评测口径纳入同一条 AI 服务主线。
```

### 结果页结尾

> 我的亮点不在于让模型输出更长的报告，而在于让调查过程变得可见、可干预、可回滚、可重新验证，并且能够用统一指标比较它到底解决了什么问题。

## 五、与后续 7 页的衔接

如果把这两页放入 7 页 PPT，推荐顺序改为：

1. User Story：用户为什么需要“可演进证据链”；
2. Result / Showcase：调查树如何实际变化；
3. AI 设计：假设、证据、隔离和上下文治理；
4. Ideal：理想的可干预、可回滚调查服务；

7. 赛道结果、个人亮点与边界。

## 六、建议固定使用的核心概念

为了让评委记住这个差异点，建议不要每一页换一种说法，可以固定成下面两个概念：

### 1. Evidence Admission：证据准入

> AI 只能使用自行申请并获准的 Evidence，或用户明确添加的 Evidence。

它强调证据如何进入当前调查，避免“数据库里有”被误解成“模型天然可见”。

### 2. Independent Evidence Workspaces：独立证据工作区

> 不同调查链路默认独立；证据共享必须显式授权、校验并记录。

它强调不同假设、不同 Agent 或不同评测分支之间不会因为共用一个 Case 或数据库而自动共享上下文。

### 两个概念合并后的核心卖点

```text
证据如何进入：Admission
证据在哪里可见：Workspace Isolation
证据如何改变结论：Revision / Invalidation / Re-exploration
```

可以在答辩中把它总结为：

> Mini-Drop 不给 AI 一个全局证据仓库，而是给它一个经过准入控制的、属于当前调查链路的 Evidence Workspace。
