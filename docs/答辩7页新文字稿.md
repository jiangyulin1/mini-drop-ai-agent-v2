# Mini-Drop 答辩 7 页新文字稿

> 版本：v0.2  适用：7 页、约 8–10 分钟  
> 叙事方式：一个复合事故贯穿 User Story、AI 处理、Showcase、架构、难点和结果。

## 贯穿场景

生产环境 `checkout` 服务从上午开始间歇性超时：首页正常，但购物车和支付链路受影响；部分实例 CPU 偏高，同机邻居也有波动；日志出现连接等待和请求堆积。值班 SRE 希望“自动定位，但不做生产修改”。

这个场景同时包含 CPU 噪声、Runtime 等待、下游依赖、局部实例和时间窗错位等竞争解释，能够展示完整的 AI 调查思路。

## 第 1 页：User Story

### PPT 只放

```text
checkout 间歇性超时
首页正常，支付链路受影响

CPU？Runtime？下游？
```

画面：`frontend → checkout → payment / redis` 服务链路，旁边放 P99、timeout、实例异常三个信号。页脚：`只读调查 · 不做生产修改`。

### 演讲稿

我们面对的不是一个简单的“服务挂了”，而是局部、间歇性、带噪声的性能问题。现有监控能够看到超时现象，却不能直接区分 CPU 压力、运行时等待、IO 阻塞还是下游依赖。用户还明确要求只读调查，因此 AI 必须在安全边界内工作。

Mini-Drop 的目标不是把问题直接丢给模型，而是把一个含噪、含冲突、带约束的问题，转化为可验证的信息目标。

## 第 2 页：AI 上下文治理

### PPT 只放

```text
原始世界：大、杂、会变化
          ↓
Task-specific Snapshot
          ↓
目标 / 时间窗 / 缺口 / 高价值 Evidence
```

画面：raw logs、metrics、profiles、topology 经过 `Projection / Budget / Redaction` 漏斗，输出本轮 Snapshot；旁边画 Branch A、Branch B 两条隔离路径。

### 演讲稿

复杂调查的第一个问题是上下文过载。我们不把原始日志和整份 profile 直接塞进 Prompt，而是先生成有界 Projection，再构造本轮 Task-specific Snapshot。Snapshot 优先保留目标身份、时间窗、当前缺口、关键指标、Evidence hash 和正在执行的任务；无关历史和超预算字段被裁剪，但原始 Artifact 仍然可以追溯和下载。

这里所说的“提高模型注意力”，更严谨的表达是：通过确定性上下文治理降低噪声，提高有效信息密度和引用稳定性。它是设计目标，不能直接说成已经测得某个注意力提升百分比。

更重要的是，AI 并不默认拥有系统中的全部 Evidence。当前模型能够使用的证据只有两个入口：AI 根据当前 Evidence Gap 自行申请并通过门禁获得的证据，或者用户明确添加到当前调查中的证据。系统里存在某条 Evidence，不等于它自动进入本轮 Prompt。

同时，调查分支默认只看到公共初始 Evidence 和自己的新证据。一个分支验证 CPU，另一个分支验证下游依赖，早期猜测不会自动污染另一条路径。不同链路之间默认独立，只有用户或治理流程显式共享，并通过目标身份、时间窗、版本和信任校验后，证据才会进入另一个分支。

本页关键词：

```text
裁剪 Compaction | 隔离 Isolation | 版本 Revision
```

## 第 3 页：AI 调查与主动采集

### PPT 只放

```text
Hypothesis
    ↓
Evidence Gap
    ↓
Collector Proposal
    ↓
Evidence / Stop / Abstain
```

画面：第一轮已有 `sys_metrics` 和日志摘要；第二轮根据缺口选择 `runtime_snapshot` 或 `connection_probe`。

### 演讲稿

AI 不需要第一轮就给出根因。它先维护多个竞争假设，说明每个假设由哪些证据支持、还缺少什么事实，再选择最能区分这些假设的已注册 Collector。

例如 CPU 指标只能说明某个实例很忙，却不能说明请求是否卡在锁等待或下游连接上。这时更有价值的下一步可能是运行时快照或连接探测，而不是再次采集同一类 CPU 数据。

模型只生成结构化 `CollectorProposal`。Server 会检查目标、能力、参数 Schema、风险、预算、审批、幂等键和 revision，之后才编译为原生 Task。证据仍不足时，Agent 可以继续补证，也可以明确提交 `INSUFFICIENT_EVIDENCE`，而不是强行闭合根因。

因此，AI 的“可见世界”不是全局数据库，而是由当前分支中 AI 已申请获得、或用户明确添加的 Evidence 组成的受控集合。

## 第 4 页：Showcase 全展示

### PPT 只放

```text
采集 → 证据 → 分支 → 结论
              ↓
        人工排除 / 重新验证
```

画面：使用实际 Workspace 截图或 3–4 张连续界面截图。

### 演示和演讲顺序

1. 创建 Case，展示服务、环境、目标进程和只读策略。
2. 创建隔离分支，说明不同分支的 Evidence 可见性不同。
3. 展开 Projection，展示 Evidence ID、目标、时间窗、hash 和字段摘要。
4. 提交带引用的结论，允许状态为 `PARTIALLY_CONFIRMED`。
5. 将一条误导性 Evidence 标记为 `EXCLUDED` 或 `LOW_TRUST`。
6. 展示关联 Analysis 变为 `STALE_INPUT`，Workspace 进入 `RECHECK_REQUIRED`。
7. 展示重新验证：历史结论保留审计价值，但不能继续作为当前结论。

### 演讲稿

Showcase 展示的不是一段漂亮的模型回答，而是 Evidence 进入、结论形成、人工纠正和旧结论失效的完整状态变化。

## 第 5 页：AI 功能总体架构

### PPT 只放

```text
Interaction & Intent
          ↓
Context Governance
          ↓
Reasoning & Planning
          ↓
Evidence Acquisition / Analysis
          ↓
Human Review + Verifier
```

右侧贯穿一条确定性控制面：`Scope / Policy / Budget / Revision / Audit`。底部连接 Worker、Analyzer 和 Evidence Store。

### 演讲稿

从 AI 功能角度看，Mini-Drop 不是一个 Chat Completion，而是五个能力层：理解意图，治理上下文，维护假设和缺口，选择并分析 Evidence，最后经过人工 Review 和确定性 Verifier 提交结论或拒答。

这些 AI 能力都运行在确定性控制面之内。AI 负责探索，系统负责身份、范围、权限、风险、预算、证据生命周期、引用校验和最终状态提交。

三个关键设计：

- `Context Snapshot`：每轮重建当前世界，不依赖 Sidecar 内存；
- `Artifact / Evidence / Projection`：原始产物、业务证据和模型视图分离；
- `Branch + Revision + Fencing`：证据隔离、状态可回退、迟到写入不能覆盖当前结论。

这里的证据隔离不是 Prompt 层面的提醒，而是可见性规则：不同调查链路默认独立，Evidence 只能通过“AI 申请”或“用户添加”进入当前链路，跨链路共享必须显式发生并留下 revision 和审计记录。

技术选型的逻辑是：Pi 解决长周期 Agent loop，原生 Task/gRPC 解决 Linux 深度采集，SQL/Outbox 解决异步恢复，Projection 解决上下文预算和引用验证。

## 第 6 页：严重障碍与克服

### PPT 只放

```text
太多 → 看不见重点
串线 → 分不清来源
过时 → 旧结果覆盖新状态
          ↓
Projection + Isolation + Fencing
```

### 演讲稿

开发中最严重的障碍不是接通模型 API，而是长周期异步调查中的上下文与证据失真。

第一，原始 Artifact 太大，模型容易错过真正区分假设的字段。第二，不同分支、不同时间窗或已经排除的 Evidence 可能串到一起。第三，Worker、Analyzer 或 Sidecar 重启后，旧代次的结果可能晚到并覆盖新结论。

我们用三层机制解决：

1. **Projection**：确定性裁剪，保留 hash、身份、时间窗和高价值字段；
2. **Isolation**：branch-local 可见性，跨分支共享必须显式授权；
3. **Fencing**：revision、generation 和幂等键保证旧结果只能留在历史中，不能写入 current。

因此，系统不只是控制“模型记得什么”，还控制“模型允许看到什么、引用什么、写回什么”。人工 Review/Exclude 会触发 stale propagation 和新一代 revalidation，人工纠正因此成为推理状态的一部分，而不是一个 UI 标签。不同链路的证据不会因为同处一个数据库就自动共享。

## 第 7 页：结果、成功率、边界与价值

### PPT 只放

```text
27/27  Provider + Runtime 结构闭环
27/27  Evidence ID / Hash 完整引用
9.2–9.6/10  非双盲公开 PR 人工粗评

不是通用 RCA 准确率
```

页脚：`Pi/Sidecar · Native Task · SQL/Outbox · Evidence Ledger`。

### 演讲稿

结果需要分三种口径理解。

第一，工程链路层面，Evidence-native 9×3 矩阵使用真实 DeepSeek Provider 完成 9 个案例、每个 3 轮，共 27 轮；`27/27` 完成并通过结构门禁。这证明 Runtime、只读策略、工具审计、Evidence 绑定和多轮链路是通的。

第二，证据绑定层面，第一轮只有 `8/27` 轮完整写出三份 canonical Evidence ID。收紧答案合同重新运行后，达到 `27/27` 轮完整绑定 Evidence ID 和 Projection hash。这说明发现引用缺口后，可以通过工程约束修复，而不是只评价模型输出好不好看。

第三，质量信号层面，在给定公开 PR 和 Projection 的非双盲人工/Oracle 评估中，综合粗评约 `9.2–9.6/10`。它反映机制归因、Evidence 引用、反证与不确定性、影响边界，不是通用生产 RCA 准确率。

因此当前可以诚实宣称：我们完成了一个可运行、可审计、可纠正、可评测的 Evidence-native AI 调查闭环；不能宣称通用自动修复、正式盲测准确率或生产自治。

### 结束句

> Mini-Drop 的价值不是让模型更大胆地猜，而是让它在更少、更相关、彼此隔离且可验证的上下文中行动；当证据不足或被推翻时，它也能有依据地停止和重新调查。

## 结果数字口径

| 数字 | 可以说明 | 不能说明 |
|---|---|---|
| `27/27 completed` | 公开 9×3 Runtime/Evidence 结构闭环 | 通用 RCA 准确率 |
| `27/27 citation-complete` | Evidence ID/hash 完整引用 | 每个机制判断都正确 |

## 追问：裁剪上下文真的提高注意力吗？

> 我们把它定义为上下文治理能力，而不是未经实验验证的心理学结论。Projection 会裁剪无关字段、限制字节预算、保留目标、时间窗、缺口和高价值 Evidence。直接可验证的收益是上下文大小受控、字段引用稳定、hash 可复核；“注意力提高”仍需要同一 Case、同一模型、同一预算下的 paired ablation 才能证明。

## 追问：隔离证据的价值是什么？

> 隔离不是为了让模型少看信息，而是为了让每条推理的来源可解释。不同分支默认只看到公共 Evidence 与本分支结果；共享前必须校验目标身份、时间窗、Collector 版本、Review 状态和 Projection hash，并创建新的 revision。这样可以防止早期猜测互相污染，也能把 Agent 的探索路径做成公平评测对象。
