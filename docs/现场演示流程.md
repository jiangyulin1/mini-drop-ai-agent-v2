# Mini-Drop 现场演示流程（客户演示脚本）

> 适用：向客户/评审展示「AI 性能诊断与恢复」设计能力与业务链。
> 演示环境已部署完成：control 192.168.10.10 / worker1 / worker2，被测服务为
> OpenTelemetry Demo product-catalog（Go）+ PostgreSQL，Agent 注册 10 种能力。
> 演示时长：精华版约 15 分钟，完整版约 35 分钟。

## 阶段 1：开场 + 产品浏览（5 分钟）

### 1.1 开场白（约 1 分钟）
> "这是我们为**基础运维人员**设计的 AI 性能诊断产品。用户不需要懂 PID、探针、火焰图，
> 只要用一句话描述现象，系统自动完成发现、采集、归因、验证的完整闭环。
> 今天现场跑的是真实环境——三节点集群 + GitHub 开源项目，不是演示数据。"

### 1.2 打开浏览器（约 2 分钟）
1. 浏览器打开 **https://192.168.10.10/**（自签名证书，点「继续访问」）
2. 讲解三个入口：
   - **采集与监控**：Agent 状态（两个 worker ONLINE）+ 任务面板 + 诊断数据台
   - **AI 诊断**：与 AI 对话的交互窗口
   - **设置**：AI 配置 / 健康检查 / 审计日志 / 存储维护
3. 强调：**所有内部概念（12 步流水线、探针、step_id）都藏在技术抽屉里**，基础用户界面只有两页。

### 1.3 进程发现演示（约 2 分钟，第一页）
1. 在「采集与监控」页点击 **多机采集** → 选 worker1
2. 范围选择弹窗：搜索框输入 `catalog` → 点击搜索
3. 预期：自动列出 `product-catalog（PID 5755）` 候选（**无需手工填 PID**）
4. 勾选 → 下发 `sys_metrics` 采集 → 查看实时指标曲线
5. 强调：这是「P0：消除填 PID 门槛」的落地——服务名 → 进程自动匹配。

## 阶段 2：演示 A —— CPU 热点诊断（6 分钟）

### 2.1 注入故障（Windows 端执行）
```bash
python scripts/demo_control.py inject cpu
```
（后台：eval-load 高并发压测 product-catalog 的 gRPC 端点，持续 120 秒）

### 2.2 浏览器操作（AI 诊断页）
1. 切到 **「AI 诊断」** 页 → **新建 Case**
2. 填写：
   - 问题描述：`product-catalog 从几分钟前开始响应变慢，CPU 占用很高，能帮我看看是什么原因吗`
   - 服务范围：选 worker1 / product-catalog（搜索 `catalog` 自动带出）
   - 点「开始诊断」

### 2.3 观察与讲解（预期 60~90 秒出结论）
- 界面会显示诊断推进：自动执行 `系统指标`（R1 低风险自动）→ 采集完成后建议 `CPU Profile`（R2，需用户确认一次）→ 点「批准」
- 结论卡出现：**根因位置=自身(self)**、**领域=cpu**、置信度+证据 4 条
- 强调：**用户全程只做了两件事——说了一句话 + 点了一次确认**。

### 2.4 展示结论卡细节
- 证据列表（可点开看原始采集产物）
- 「建议的下一步」：此处会显示「验证恢复」或继续引导
- 「查看证据」按钮 → 技术抽屉（面向技术型客户的加分项）

## 阶段 3：演示 B —— 下游故障诊断（6 分钟）

### 3.1 清理 A + 注入 B
```bash
python scripts/demo_control.py clean
python scripts/demo_control.py inject pg
```
（后台：停止 PostgreSQL + 低并发压测触发连接失败日志，持续 120 秒）

### 3.2 浏览器操作
新建 Case，问题描述：
`product-catalog 大量报错，查询商品不可用，日志里好像有连接拒绝`

### 3.3 观察与讲解
- 诊断自动执行 **`日志扫描`（R1）** + 系统指标
- 结论卡：**根因位置=下游(downstream)**、**领域=network**，摘要含
  「日志出现 500 次连接类错误（refused），优先怀疑下游依赖」
- 证据里可展开日志扫描产物，看到真实的 `connection refused` 错误行
- 强调：**这是"报错类"问题——用日志证据定位，而不是猜**；且系统能区分
  「自身 CPU 高」与「下游不可达」（即使 CPU 也偏高，连接错误证据优先）。

### 3.4 （可选加分）展示「多轮引导」
- 若诊断显示证据不足，会给出「建议的下一步：扫描进程日志」等引导卡片
- 强调：基础用户不会被"证据不足"卡住，系统会告诉他下一步最值得做什么。

## 阶段 4：演示 C —— 无故障诚实性（4 分钟，客户最关心）

### 4.1 清理 B
```bash
python scripts/demo_control.py clean
```

### 4.2 浏览器操作
新建 Case，问题描述：`product-catalog 好像偶尔有点慢，帮我检查一下有没有问题`
（此时环境已完全恢复，无任何故障）

### 4.3 预期与讲解
- 结论：**证据不足（insufficient_evidence）**——**不强行给出确定根因**
- 强调：**安全第一**——LLM/系统不得在无故障时伪造根因；这是评测的硬性指标之一
  （no-fault 误报=0），也是客户信任的关键设计。

## 阶段 5：（可选）恢复验证闭环演示（5 分钟）

前提：演示 A 或 B 的结论已生成。
1. 在结论卡「建议的下一步」看到**「触发验证采集」**按钮（type=verify 时）
2. 用户执行建议动作后，点「验证恢复」→ 系统用**相同参数重新采集** sys_metrics（10s）
3. 展示指标对比：`process_cpu_cores 1.5 → 0.4（recovered）` 等
4. 强调：**No-Regression 判定**——不仅看"好了没"，还看"有没有新退化"（degraded）。

## 附录 B：演示中途故障处理

| 现象 | 处理 |
|---|---|
| 诊断 2 分钟无结论 | `watch` 查看状态；若 `WAITING_APPROVAL`，回到界面点「批准」；若 `INSUFFICIENT_EVIDENCE` 属正常（无故障时） |
| product-catalog DOWN | worker1 上 `/opt/mini-drop-eval/start.sh`（需 MINI_DROP_EVAL=1 环境已写入脚本） |
| PG 不可用 | `sudo systemctl start postgresql` |
| 页面打不开 | 检查 nginx：`systemctl is-active nginx`；浏览器清缓存 |
| 压测残留影响后续 | `python scripts/demo_control.py clean` + 等 135 秒（复用窗口）再继续 |
| 场景顺序错乱 | 每场演示前先 `clean`，再做下一个 |
