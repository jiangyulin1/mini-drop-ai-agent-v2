## 0. 评测方法

- **AI 功能定义**：本平台三个 AI 参与点——NLP 意图解析、RCA 归因推理、结果总结。实测当前诊断链中 LLM 仅参与**意图解析**（`diagnosis-intent.v1`，见 §4），RCA 分类与结论由确定性分析器（`RulesOnlyReasoner` → `assess_cluster`）产生，LLM 不参与推理，结论可完全追溯到结构化证据。
- **链条评分维度**（`score_audit_bundle`，满分 100）：
  | 维度 | 满分 | 含义 |
  |---|---|---|
  | 根因定位 | 40 | location_type / domain_type / classification 命中 oracle |
  | 证据 | 25 | 引用有效 10 + 采集召回 8 + 独立来源 4 + 质量门 3 |
  | 运行轨迹 | 20 | 链完整性 5 + 阶段覆盖 5 + 轨迹引用 5 + 候选替代 5 |
  | 安全 | 10 | 无未授权动作 5 + 无禁用动作 5 |
  | 恢复 | 5 | 可恢复且回滚验证通过 |
- **Oracle 隔离**：oracle 数据只存在于本地 `benchmarks/ai_ops_v2/private/oracles.json`，VM 只下发公开 query，评分在本地私有侧进行。

### 2.1 OB-SINGLE-NOISY-CPU-001（期望 same_host/cpu/noisy_neighbor）
- AI 结论：`downstream + network + downstream_dependency`（conf 0.82）
- 原因：checkoutservice 日志出现 166 次连接类错误，级联判断中 `target_connectivity` 优先于 `neighbor_cpu_pressure`，把 CPU 饥饿的错误风暴误判为下游依赖故障。

### 2.2 OB-SINGLE-PARTITION-001（期望 downstream/network/network_degradation）
- AI 结论：`self + unknown + runtime_stall`（conf 0.65）
- 原因：overlay 分区导致 frontend→cartservice 不可达；runtime_thread_snapshot 显示线程停止，确定性逻辑将其归为 self/runtime_stall；连接探针未把"路径分区"识别为下游不可达。

### 2.3 OB-COMPOUND-CROSS-WORKER-001（期望 shared_resource/[memory,network]/compound）
- AI 结论：`downstream + network + downstream_dependency`（conf 0.65）
- 原因：只识别到 checkout 的 network 根因，未把 worker1 上 frontend 的 memory 压力纳入强原因 → 未触发 compound_incident。

### 4.2 诊断链条 AI 调用结构

```
用户 query
  └─ AI ① 意图解析 (diagnosis-intent.v1, LLM, 记录 tokens/latency)
       └─ 探针选择 (choose_probe_ids, 确定性)
            └─ 采集执行 (sys_metrics / log_scan / runtime_snapshot / connection_probe ...)
                 └─ 域分析器 (domain_analyzers, 确定性)
                      └─ 分类推理 (RulesOnlyReasoner → assess_cluster, 确定性)
                           └─ root_entity 解析 (确定性)
                                └─ 结论组装 (root_location / domain_cause / conclusion)
```

每条 AI 调用记录字段：`provider / model / model_snapshot / prompt_version / output_schema / status / latency_ms / input_tokens / output_tokens / response_hash / error_code / started_at / finished_at`。原始推理与凭据不入库（`case_model_attempts` 只存元数据）。

## 5. 最新测试集（online-boutique，8 案例）覆盖测试

> 测试集 `testsets/real/online-boutique`（本合并新增）。部署适配：swarm 已跑 v0.8.0 镜像，容器定位动态解析；stress-ng 缺失改用 `yes`/python 燃烧器；currencyservice 固定到 worker2 匹配拓扑。

### 5.1 适配过程发现的 BUG 与逻辑优化（已修复并热补丁到 VM）

| 缺陷 | 修复 | 影响案例 |
|---|---|---|
| `noisy_neighbor` 症状探针映射缺 `process_cpu_profile`，无法区分"自身热点 vs 噪声邻居"，目标进程 CPU 仅主线程、Go/Python 热点在子线程 → 漏报 insufficient | `choose_probe_ids("noisy_neighbor")` 增加 `process_cpu_profile` | ob-cpu-hog、ob-same-host-noise |
| `_domain_cause` 慢速内存泄漏（slope≥1MB/s 但 RSS<256MB）不被 pressure.memory 覆盖 → domain=unknown | `_domain_cause` 对齐 memory_pressure_analyzer 的 rss_growth 判定 | ob-memory-leak |
| `_domain_cause` 缺 fd/句柄耗尽检测 → connection 案例 domain=unknown | 增加 fd≥1000 或 fd 递增≥200 → `network/fd_or_socket_exhaustion` | ob-conn-exhaust |
| 容器内独立进程（yes/stress）燃烧 CPU 但主进程 CPU 低，sys_metrics 只测主线程 → cpu 压力漏报 | sys_metrics 采集器新增 cgroup `cpu_core_usage`（cpu.stat usage_usec 差分），`_pressure_flags` 取 `max(进程,容器)` | ob-downstream-cpu、ob-cpu-burst |

**待修复**：诊断探针只覆盖 target+同宿主实例，不覆盖跨宿主下游实例（ob-downstream-cpu 的 currencyservice 无法被采集）；ob-cpu-burst 瞬态需 continuous_perf 回补窗口；ob-network-delay 需隔离网卡（FAULT_IFACE）未配置。
