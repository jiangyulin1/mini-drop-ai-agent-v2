# 自主运维 Agent 验证报告

## 结论

本轮已完成自主运维 Agent 的主链路设计和首个真实自动处置闭环：

`持续会话 → 采集 → 证据清洗 → 根因分析 → 补充采集 → 动作校验 → 执行 → 业务验证 → 稳定确认`

当前能力可用于复杂环境中的受控诊断，也已能在预授权范围内自动恢复无状态 Swarm 服务。它还不能无条件接管所有生产事故：目前只有注册动作可以执行，磁盘、网络、OOM 和运行时锁问题尚未配置通用自动修复动作。

## 已实现能力

### 持续交互与状态

- Case 保存目标范围、服务关系、诊断会话、当前结论、待确认事项、动作和恢复状态；
- 后台循环不依赖浏览器保持打开；
- 动作下发前保存确定性执行键；Control 重启后复用同一个远程任务，不重复变更；
- 支持暂停、继续、停止、人工纠正和单步推进；
- 诊断数据可通过 Case ID、诊断 ID 和任务 ID 在 AI 会话中引用；
- 前端默认显示结论、影响、动作和需要用户确认的内容，详细证据和内部过程按需展开；
- 保留独立诊断数据台、Worker 状态、多机采集、数据预览、下载、AI 分析和火焰图。

### 前端交互收敛

- 顶部只保留 AI/数据台切换、帮助入口和 Worker 状态；
- 会话头部的低频操作合并到“更多”，暂停/继续和标记解决仍直接可用；
- 诊断结果只保留“查看证据与采集详情”主操作，采集与范围入口不再重复出现；
- 用户查看历史消息时，自动刷新保持当前位置；仅在用户停留底部时跟随新消息；
- 已解决或已停止的只读会话不再显示无效输入框。

### 数据采集

| 采集器 | 用途 | 本轮验证 |
|---|---|---|
| `process_scan` | 发现进程、容器、Swarm 服务和新 PID | 双 Worker DONE |
| `sys_metrics.v2` | CPU、内存、OOM、磁盘、TCP、PSI、进程趋势 | OOM、磁盘、网络诊断通过 |
| `runtime_snapshot.v1` | Java、Go、Python 运行时和锁等待 | 三种运行时通过 |
| `log_scan` | 限量读取目标容器日志并识别错误模式 | ENOSPC、timeout 证据通过 |
| `perf_cpu` | CPU Profile、TopN、火焰图 | 已在真实服务验证 |
| `ebpf_io` | I/O 行为和热点 | 已在 VM 验证 |
| `memory_smaps` | 进程内存构成 | 已纳入诊断链路 |
| `swarm_actuation` | 受控执行 Swarm 重启或回滚 | 支付服务闭环通过 |

采集器由平台按诊断策略调用。模型负责理解问题、选择候选方向和生成可读结论，但不能执行任意 Shell 命令。事实提取、证据清洗、动作权限和恢复判定均由确定性规则完成。

### 证据处理与根因分析

- 相同目标、相同事实、相关来源的重复证据合并，不重复提高置信度；
- 失败采集不会被当作业务故障证据；
- 超出事故时间窗的数据降权；
- 只有具备对应能力的采集器才能形成反证；
- 高质量独立证据冲突时阻止自动处置；
- RSS 增长需要满足斜率、增量和持续增长条件，过滤正常波动；
- 磁盘同时检查使用率、可用字节和 ENOSPC，覆盖 ext4 保留块场景；
- TCP 重传和超时直接证据优先于笼统日志标签；
- 多个高分、跨领域原因同时成立时输出 `compound_incident`，保留主因和贡献原因；
- 报告校验检查证据引用、知识引用和动作，避免无依据结论。

## 自动处置闭环

真实案例：`case_20260810_193256_c207726c0c`

- 故障：暂停真实 `boutique_paymentservice` 容器，结算请求超时；
- 诊断：`diag_session_20260810_193321_e690252f`；
- 动作：通过 `linux-worker-1` 执行注册动作 `swarm.restart-stateless-service`；
- 约束：服务必须在允许列表中，并带有无状态和允许自治标签；
- 结果：服务 PID 从 17694 更新为 18138；
- 验证：加入购物车和结算事务连续两轮成功；
- 最终状态：Case `RESOLVED`，动作 1 次，稳定验证 2 次。

动作执行前检查授权模式、动作白名单、影响等级、环境、服务标签、当前版本、可回滚性和变更冻结状态。验证失败时进入回滚和重新诊断，不由模型自行判定“已恢复”。

Control 重启边界也已加固。每个逻辑动作在 Case 中持久保存 `operation_key`，远程 preflight、execute 和 rollback 使用由该键生成的幂等任务键。真实支付服务重复提交验证中，两次预演返回同一个远程任务，两次执行也返回同一个远程任务 `task_20260810_204012_167b17`；Swarm 版本只从 407 更新到 421 一次，之后购物车返回 302、结算返回 200。

真实回滚执行也已验证：`swarm.rollback-service` 通过远程任务 `task_20260810_204814_d8938a` 完成，Swarm 版本从 421 更新到 434；回滚后购物车返回 302、结算返回 200。自动循环测试确认恢复验证失败时会调用该回滚动作、清除旧诊断并开始新一轮调查。

## 根因准确率

准确率使用 10 个故障注入前已经记录预期答案的案例计算，不使用 `verified_vm` 环境评分代替诊断准确率：

- 严格根因命中：8/10，80%；
- 部分命中：1/10，10%；该案例命中实例、位置和 CPU 故障域，但预设分类名称不是当前规范名称；
- 证据不足：1/10，10%；支付服务停顿没有形成可靠根因；
- 可接受匹配率：9/10，90%；
- 安全处理覆盖率：10/10，100%，表示系统能够给出结论、部分结论或安全停止，不表示根因全部正确；
- 未观察到未经授权的自动动作：0 次；
- 自动恢复真实案例：1/1 成功。该样本太少，不能表述为通用 100% 恢复率。

支付案例在根因证据不足时没有猜测。系统使用真实结算请求确认服务不可用，然后执行预授权的无状态服务重启，并连续验证两次。逐案例数据见 `diagnosis_accuracy_20260811.json`。

## 面向基础使用者的展示

前端不再只显示分类代码和简短结论。当前结论区域增加：

- 这个问题用日常语言如何理解；
- 可能对服务造成什么影响；
- 系统实际看到了哪些事实；
- 每项事实由多少条原始证据支持；
- 仍缺少哪些数据；
- 本次置信分的来源，以及“置信分不等于历史准确率”的说明；
- 建议处理顺序和恢复验证方法。

工作台增加“能力与准确率”入口，说明 80%/90%/100% 三种指标的区别、适用流程、可用故障范围和当前不能安全处理的操作。

## `verified_vm` 基线

原有 VM 基线仍为 100/100：双 Worker 部署、8 个真实故障各两轮、网络分区、磁盘耗尽、Control 重启恢复、30 分钟稳定性、产物下载和火焰图均已通过。详细记录见 `REPORT_20260810.md` 和 `verified_vm_20260810.json`。

## 当前不足

1. 自动处置动作面较窄。已验证的是无状态 Swarm 服务重启；OOM、磁盘、网络和锁竞争只有诊断，没有通用自动修复。
2. 缺少 Prometheus SLO、请求级指标和 OpenTelemetry Trace。跨服务因果关系仍依赖服务关系、系统指标、日志和显式业务探针。
3. Java 目前没有 JFR 深度分析，Go 没有 block/mutex pprof 深度分析，Python 没有 GIL/asyncio 结构化分析；`runtime_snapshot` 主要提供低开销症状识别。
4. 动作 attempt 尚未形成支持多 Control 副本的持久租约。Control 单实例重启可恢复，但不等于高可用控制面。
5. 两台 Worker 位于同一物理 Hyper-V 主机，未验证跨物理故障域。
6. VM 不能访问官方镜像仓库，当前依赖校验过的离线镜像包。
