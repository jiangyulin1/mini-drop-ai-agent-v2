# Mini-Drop 十分钟演示模板

## 演示前完成（不计入十分钟）

1. 打开 `https://192.168.10.10/`。
2. 如果页面提示“访问认证失败”，在虚拟机执行：

   ```bash
   grep '^MINI_DROP_API_KEY=' /home/control/mini-drop-active/deploy/env/control-native.env | cut -d= -f2-
   ```

   将结果粘贴到页面右上角并点击“保存”，刷新后确认两台 Agent 可见。
3. 执行 `/home/control/mini-drop-demo/run-presentation-check.sh`，确认 `8/8 通过`。

## 0:00–1:00｜项目目标与异常背景

**页面：任务面板**

> Mini-Drop 面向 Linux 集群性能诊断。Agent 负责低侵入采集，服务端统一保存任务状态、
> 原始证据和可视化结果，AI 只基于真实证据进行归因。

指出 `worker2` 仍为 ONLINE：

> 当前异常发生在虚拟机之间的证据上传链路，Agent 心跳仍然正常，因此不能只凭
> “在线”状态判断整个采集链路健康。

## 1:00–3:00｜用户在 Web 主动采集

在任务面板的“快速采集”中填写：

- 采集器：系统指标
- Agent：`worker2 · ONLINE`
- PID：`1`
- 时长：`10s`

点击“开始采集”并进入任务页面。系统会自动生成直观的任务名称
`系统指标采集 · linux-worker-2 · PID 1`。

> Agent 会真实执行系统指标采集，但任务会在证据上传阶段失败。我们先不看真实原因，
> 只把它当成用户看到的异常现象。

## 3:00–4:30｜查看可见异常

展示 FAILED 状态和状态时间线中的上传失败原因：

> 这里能看到 Agent 在线、任务确实被执行，但证据没有进入对象存储。
> 单看任务失败还不能判断是采集器、权限、存储还是网络问题。

## 4:30–7:30｜用户主动使用 AI

点击页面右上方蓝色 **“运行诊断”**。AI 通常需要约一分钟。

展示“对象存储上传链路异常”、置信度、任务事件和 Agent 健康证据：

> AI 将“Agent 在线”和“证据上传失败”交叉起来，排除了 Agent 整体离线，
> 将原因收敛到 Agent 到 MinIO/S3 的跨主机网络、防火墙、TLS 或凭据链路。

展开“修复计划”：

> 建议依次检查 TCP/9000、目标 endpoint、防火墙、TLS、bucket 和访问凭据。
> 系统不会自动修改防火墙。

## 7:30–9:00｜公布真实根因

> 真实根因是控制虚拟机中的定向防火墙规则：只拒绝
> `192.168.10.12 → 192.168.10.10:9000`。这正是 worker2 到 MinIO 的证据上传路径。

## 9:00–10:00｜总结

> 这个案例展示的是：用户在 Web 中主动采集、看到真实失败、调用 AI，
> AI 再根据任务事件和 Agent 状态推断跨虚拟机链路问题，而不是脚本预先写好答案。

演示结束后执行：

```bash
sudo /home/control/mini-drop-demo/storage_link_fault.sh recover
```

## 现场备用

如果需要重新启用异常：

```bash
sudo /home/control/mini-drop-demo/storage_link_fault.sh apply
```
