# Mini-Drop 现场演示流程

建议控制在 10–12 分钟。主演示为“真实故障注入—采集—AI 归因—服务恢复”；
已经完成的任务作为现场网络或模型异常时的备用方案。

## 开始前

在虚拟机执行：

```bash
cd /home/control/mini-drop-demo
./run-presentation-check.sh
```

只有结果显示 `8/8 通过` 后再开始演示。浏览器入口为 `https://192.168.10.10/`。
如果页面提示“访问认证失败”，说明当前浏览器没有保存 API Key：从
`/home/control/mini-drop-active/deploy/env/control-native.env` 读取
`MINI_DROP_API_KEY`，粘贴到页面右上角并点击“保存”。

十分钟版本可直接使用同目录下的《十分钟演示模板.md》。

## 演示顺序

1. **环境状态（约 1 分钟）**
   - 展示两台 Linux Agent 均为 ONLINE。
   - 执行预检，说明 Server、数据库、对象存储、证据下载均已通过。

2. **启动完整故障演示（约 1 分钟）**

   ```bash
   sudo /home/control/mini-drop-demo/run-live-incident.sh prepare
   ```

   - 脚本启动隔离的 checkout 演示服务与临时 Agent。
   - 正常模式建立延迟基线，然后切换到 CPU/JSON 序列化异常模式。
   - 脚本只完成证据采集，不调用 AI；由演示者在 Web 中点击“运行诊断”。
   - 负载受 `CPUQuota=80%`、`MemoryMax=192M` 和最长运行时间保护。

3. **观察异常并由用户启动 AI（约 5 分钟，核心）**
   - 页面中新任务名称为“现场演示｜checkout 服务 CPU 与 JSON 序列化异常”。
   - 任务经历 PENDING、RUNNING、UPLOADING、ANALYZING、DONE。
   - 在火焰图搜索框输入 `cpu_hotspot`，展示帧高亮。
   - 点击热点帧放大，再点击“重置”返回全局。
   - 点击右侧 TopN，说明图表与函数排名联动。
   - 点击页面右上方蓝色“运行诊断”，模拟用户主动请求 AI 分析。
   - 展示 AI 摘要、候选原因、置信度、证据引用和结构化工具检查。
   - 说明 eBPF 对 py-spy 任务“不适用”，baseline 是“可选”证据。

4. **恢复验证（约 1 分钟）**
   - 执行 `/home/control/mini-drop-demo/run-live-incident.sh recover`。
   - 服务切回 normal 模式并重新测量恢复后延迟。
   - 诊断结果和火焰图会保留，演示服务不需要继续保持异常。

5. **结束清理**

   ```bash
   sudo /home/control/mini-drop-demo/run-live-incident.sh cleanup
   ```

   即使忘记清理，两个临时 systemd 单元也会在最长运行时间后自动停止。

## 现场表述重点

- 系统将“采集成功”和“证据足以归因”分开判断。
- 不属于当前采集器的数据标记为“不适用”，不会误报为任务失败。
- AI 输出必须引用真实证据；风险动作只生成计划，不会自动执行。
- 演示数据来自 Agent 实际采集和对象存储，不是前端写死的样例。

## 备用方案

如果现场采集或外部模型临时不可用，执行：

```bash
/home/control/mini-drop-demo/run-presentation-check.sh
```

然后按照脚本输出的四个备用任务链接展示。已保存的火焰图、TopN、系统指标、
内存趋势、eBPF 证据和已校验 AI 诊断均不依赖现场模型调用。
